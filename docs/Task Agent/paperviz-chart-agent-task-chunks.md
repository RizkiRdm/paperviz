# PaperViz Chart Engine — AI Agent Task Chunks

## Purpose

Fix and improve the PaperViz chart feature without changing the existing product roadmap.

Main rule:

> AI may interpret and transform evidence, but AI must never invent the underlying numeric data.

Target pipeline:

Paper -> Evidence extraction -> Candidate dataset -> AI chart planning -> Grounding validation -> Chart rendering

Image/chart extraction remains useful, but it is only one evidence source.

---

# Global Rules

## Rule 1 — Do not change the roadmap

Do not modify the existing Phase 4–12 roadmap structure.

These chunks are an implementation workstream for the existing chart feature.

## Rule 2 — Do not rewrite the whole application

Reuse the current architecture, services, repository layer, database schema, and frontend patterns where practical.

Only change code required for the chart system.

## Rule 3 — No fabricated numbers

Never allow an LLM-generated number to become chart data unless that number can be traced to evidence extracted from the paper.

Invalid examples:

- "improved significantly" -> inventing a percentage
- "about twice as high" -> inventing exact values
- incomplete values -> filling missing values with 0
- guessing values from a chart description

## Rule 4 — Separate responsibilities

Do not let one LLM call perform all of these jobs:

- finding numbers
- interpreting numbers
- choosing chart type
- generating chart data
- validating chart data

Separate extraction, planning, validation, and rendering.

## Rule 5 — Preserve safe existing behavior

Do not remove image fallback.

Do not remove existing chart support unless required for correctness.

# C1 — Audit Current Chart Pipeline

## Goal

Understand the current chart pipeline before changing it.

## Tasks

1. Inspect:
   - `internal/services/charts.go`
   - `internal/services/pipeline.go`
   - chart repository/model code
   - chart database schema
   - frontend chart components
   - chart tests
2. Trace:
   - PDF extraction
   - chapter extraction
   - image extraction
   - LLM calls
   - chart persistence
   - API response
   - frontend rendering
3. Identify where:
   - numbers are extracted
   - numbers are generated by LLM
   - chart type is selected
   - chart data is validated
   - chart data is rendered
4. Document current failure points.

## Known problem

The current chapter-chart path asks the LLM to produce labels, values, and chart type directly from chapter text.

This is unsafe because the model can invent or incorrectly interpret numeric data.

## Acceptance Criteria

- Current chart flow is documented.
- Unsafe points are identified.
- No behavior is changed yet.

# C2 — Create Numeric Evidence Model

## Goal

Create a structured representation of numeric evidence extracted from the paper.

Concept:

```json
{
  "evidence_id": "ev_123",
  "metric": "accuracy",
  "entity": "Model A",
  "value": 72.4,
  "unit": "%",
  "source": {
    "page": 7,
    "text": "Model A achieved 72.4% accuracy."
  }
}
```

## Minimum fields

- id
- metric
- entity
- value
- unit
- source page
- source text

Optional:

- context
- group
- experiment
- time
- confidence

## Rules

- Every numeric evidence item must have a source.
- Generated numbers are not numeric evidence.
- Preserve enough provenance for later grounding.

## Acceptance Criteria

- Numeric evidence has a clear type/model.
- Evidence points to source text/page.
- Tests cover valid and invalid evidence.

---

# C3 — Extract Numeric Evidence from Text

## Goal

Extract numbers from paper text before asking the LLM to create charts.

Useful sources:

- body text
- results sections
- comparison statements
- statistical results

Examples:

```text
"Accuracy increased from 72.4% to 81.7%."

"Model A achieved 72.4%, while Model B achieved 81.7%."

"beta = 0.42, 95% CI [0.31, 0.53]."

"Latency decreased from 120 ms to 84 ms."
```

## Rules

Preserve original meaning.

Do not assume:

```text
12% improvement
```

means:

```text
baseline = 0
new value = 12
```

Ambiguous statements must remain ambiguous.

## Acceptance Criteria

- Numeric claims become structured evidence.
- Every value has source text/page.
- Ambiguous claims are not converted into fake values.

# C4 — Extract Structured Data from Tables

## Goal

Use tables as a high-reliability chart data source.

Example:

```text
Model      Accuracy    F1
Baseline   72.4        0.68
Ours       81.7        0.76
Model C    79.2        0.73
```

Expected structured data:

```json
{
  "columns": ["Model", "Accuracy", "F1"],
  "rows": [
    ["Baseline", 72.4, 0.68],
    ["Ours", 81.7, 0.76],
    ["Model C", 79.2, 0.73]
  ]
}
```

## Rules

- Reuse existing table extraction where available.
- Do not OCR a table image if structured table data already exists.
- Preserve units, headers, and page provenance.
- Do not guess missing cells.

## Acceptance Criteria

- Table data can become a chart dataset.
- Every chart value derived from a table can be traced to a table cell.
- Missing cells remain missing, not zero.

# C5 — Build Candidate Dataset Layer

## Goal

Create a layer between evidence extraction and chart generation.

Pipeline:

```text
Numeric Evidence
      +
Table Data
      +
Statistical Evidence
      ->
Candidate Dataset
```

Concept:

```json
{
  "dataset_id": "ds_001",
  "title": "Accuracy by model",
  "dimensions": ["model", "accuracy"],
  "unit": "%",
  "points": [
    {
      "label": "Baseline",
      "value": 72.4,
      "evidence_id": "ev_1"
    },
    {
      "label": "Ours",
      "value": 81.7,
      "evidence_id": "ev_2"
    }
  ]
}
```

## Rules

- Dataset values must come from evidence.
- The LLM must not invent dataset values.
- One chapter can produce zero, one, or many candidate datasets.

## Acceptance Criteria

- Dataset exists independently from chart type.
- Dataset values retain provenance.
- One chapter is no longer limited to one chart.

# C6 — Change Chart Generation to Use Evidence

## Goal

Replace the unsafe chapter -> labels/values flow.

Old:

```text
Chapter
  ->
LLM
  ->
labels + values + chart type
```

New:

```text
Chapter
  ->
Evidence
  ->
Candidate Dataset
  ->
LLM
  ->
Chart Plan
```

The LLM may decide:

- whether visualization is useful
- which dataset to visualize
- chart type
- title
- axis labels
- takeaway
- limitations

The LLM must NOT generate numeric values.

## Acceptance Criteria

- Chart values originate from candidate datasets.
- LLM output cannot directly overwrite chart values.
- No meaningful dataset means no chart.

# C7 — Create Chart Specification

## Goal

Stop using one generic `labels + values` schema for every chart type.

## Bar

```json
{
  "type": "bar",
  "categories": ["Baseline", "Ours"],
  "series": [
    {
      "name": "Accuracy",
      "values": [72.4, 81.7]
    }
  ]
}
```

## Line

```json
{
  "type": "line",
  "x": ["1", "2", "3", "4"],
  "series": [
    {
      "name": "Accuracy",
      "values": [72, 75, 79, 82]
    }
  ]
}
```

## Scatter

Scatter requires numeric X and Y:

```json
{
  "type": "scatter",
  "x": [10, 20, 30],
  "y": [0.71, 0.78, 0.83]
}
```

Do not represent scatter as categorical labels plus one value.

## Initial priority

1. bar
2. line
3. scatter
4. pie

Pie should only be used when categories represent parts of one whole.

## Acceptance Criteria

- Schema matches chart type.
- Scatter uses numeric X/Y.
- Schema is documented and tested.

# C8 — Implement Deterministic Grounding Validator

## Goal

Prevent unsupported chart data from reaching the renderer.

## Validation rules

A chart passes only if:

1. chart type is supported
2. required fields exist
3. numeric values are numeric
4. dimensions have compatible lengths
5. units are consistent
6. every numeric value has evidence
7. every evidence ID exists
8. source page exists where required
9. missing values are not converted to zero
10. chart structure matches chart type

## Grounding status

Use:

```text
verified
partial
unsupported
```

### verified

All displayed numeric values have direct evidence.

### partial

Some transformation or interpretation is allowed and explicitly represented.

### unsupported

Values cannot be traced to paper evidence.

Critical rule:

```text
unsupported -> DO NOT RENDER
```

## Acceptance Criteria

- Validator is deterministic.
- LLM confidence cannot override grounding failure.
- Tests cover valid and invalid chart data.

# C9 — Fix Missing Value Behavior

## Goal

Prevent missing data from becoming zero.

If frontend logic does:

```text
value ?? 0
```

remove this behavior for chart data.

Missing is not zero.

## Correct behavior

If a required value is missing:

```text
validation failure
```

or explicitly represent missing data if the chart type supports it.

Never silently convert:

```text
null -> 0
```

## Acceptance Criteria

- Missing values cannot silently render as zero.
- Backend rejects invalid dimensions.
- Frontend does not invent numeric values.

# C10 — Remove One-Chart-Per-Chapter Limitation

## Goal

Make the dataset the unit of visualization.

Old:

```text
Chapter
  ->
One chart
```

New:

```text
Chapter
  ->
Evidence
  ->
Candidate datasets
  ->
0..N charts
```

Example:

```text
Results chapter
 |- Accuracy by model
 |- Latency by model
 `- Accuracy across datasets
```

Only meaningful datasets should become charts.

## Acceptance Criteria

- A chapter can produce multiple valid charts.
- A chapter can produce zero charts.
- Each chart has dataset and evidence provenance.
- No arbitrary one-chart-per-chapter limit remains.

# C11 — Keep Image Extraction as Fallback

## Goal

Keep image/chart parsing without making it the only solution.

Evidence priority:

1. structured table data
2. numeric claims from text
3. statistical results
4. figure caption + surrounding text
5. image/chart extraction

Image extraction is still valuable when numeric data exists only inside a visual chart.

## Rules

If image extraction succeeds:

```text
image -> extracted data -> validate -> render
```

If image extraction fails:

```text
image -> original image + annotation
```

If no safe interpretation exists:

```text
omit chart
```

## Acceptance Criteria

- Image fallback still works.
- Image-derived numbers are grounded before rendering.
- No unsupported chart is generated merely because an image exists.

## Goal

Possible methods:

```text

```

## Acceptance Criteria

- Backend can explain where chart values came from.
- Provenance survives API serialization.

# C13 — Improve Frontend Chart Safety

## Goal

Make frontend rendering simple and safe.

Frontend should render validated chart specifications.

Frontend must NOT:

- infer missing values
- repair invalid arrays
- invent labels
- convert null to zero
- decide whether data is trustworthy

Flow:

```text
validated ChartSpec
      ->
render
```

Display:

- chart
- title
- units
- source page
- grounding status
- confidence/limitations if available

## Acceptance Criteria

- Frontend does not modify numeric data.
- Invalid chart specs do not render.
- User can see whether a chart is grounded.

# C14 — Add Chart Failure Categories

## Goal

Make chart bugs diagnosable.

Use explicit categories:

```text
EXTRACTION_ERROR
DATASET_ERROR
CHART_SELECTION_ERROR
GROUNDING_ERROR
SCHEMA_ERROR
RENDER_ERROR
```

For each failed chart, log:

- paper ID
- page/chapter
- stage
- error category
- safe error message
- whether fallback was used

Do not log sensitive paper contents unnecessarily.

## Acceptance Criteria

A chart failure must clearly identify its pipeline stage.

# C15 — Add Regression Tests

## Goal

Prevent chart bugs from returning.

Test cases:

### Case 1 — Simple text comparison

```text
Model A = 72.4%
Model B = 81.7%
```

Expected: valid bar dataset.

### Case 2 — Table data

Expected: valid dataset with cell provenance.

### Case 3 — Ambiguous improvement

```text
"improved by 12%"
```

Expected: no fabricated baseline/new value.

### Case 4 — Missing value

```text
[72.4, 81.7, null]
```

Expected: validation failure.

### Case 5 — Scatter

Expected: numeric X + numeric Y.

### Case 6 — Invalid pie

Data does not represent a whole.

Expected: reject pie or select another chart type.

### Case 7 — Unsupported values

LLM returns values without evidence.

Expected: unsupported -> no render.

### Case 8 — Image fallback

Image extraction fails.

Expected: original image + annotation.

## Acceptance Criteria

All tests pass.

# C16 — Validate with Real Academic Papers

## Goal

Test against real paper structures instead of only synthetic happy paths.

Use a small corpus containing:

1. numeric results in body text
2. multiple tables
3. charts with data only inside images
4. statistical results
5. ambiguous narrative claims
6. multiple datasets in one chapter
7. incomplete values

Measure:

- charts generated
- charts rejected
- grounded values
- unsupported values
- false-positive charts
- false-negative charts
- fallback usage
- processing failures

Important metric:

```text
grounded generated charts / all generated charts
```

Do not optimize for number of charts generated.

A safe omission is better than a convincing false chart.

## Acceptance Criteria

The system produces fewer hallucinated charts even if total chart count decreases.

# Definition of Done

The chart system is successful when:

- AI does not invent chart values.
- Every displayed numeric value has traceable evidence.
- Tables can become chart datasets.
- Numeric claims in text can become chart datasets.
- One chapter can produce multiple meaningful charts.
- A chapter can produce no chart.
- Scatter uses numeric X/Y data.
- Missing values are never silently converted to zero.
- Unsupported data is not rendered.
- Image extraction remains available as fallback.
- Frontend only renders validated chart specifications.
- Chart failures are categorized and observable.
- Regression tests cover hallucination and grounding cases.
- Real academic papers are used for validation.
- Existing PaperViz roadmap remains unchanged.

# Core Product Principle

> PaperViz may transform evidence, but it must never manufacture evidence.

AI is the semantic layer.

The paper is the source of truth.

The validator is the gatekeeper.

The renderer only renders validated data.
